# Unified-Subtree + Global-Arbiter 对齐演化实验计划

**Problem**：现有 Phase17 在演化阶段以 node Pairwise 输出和显式递归 M1 决定错误、候选竞争与接受，但最终推理采用“五棵 Unified-Subtree 报告 → Global Arbiter”，导致优化目标与部署执行语义不一致。
**Method Thesis**：让系统级错误反馈、Split/Refine 候选竞争和 epoch 提交均由 Unified-Subtree + Global-Arbiter 执行器决定，同时保留 node Worker 作为触发与局部归因工具，应能演化出更适配最终推理系统的 Rubric。
**Date**：2026-08-28

## 1. Claim Map

| Claim | Why It Matters | Minimum Convincing Evidence | Linked Blocks |
| --- | --- | --- | --- |
| C1：执行语义对齐能改善最终系统 | 当前 Rubric 由显式递归目标选择，却由 Arbiter 部署；目标错位可能接受无效改动或拒绝有用改动 | 在完全相同的 Qwen3 Worker、Unified-Subtree Prompt、Global-Arbiter Prompt、数据和 `K=3` 评测下，新 Rubric 在 VL-RewardBench 的 Strict ACC 高于 Phase17 E4，且 paired CI/McNemar 支持正向差异 | B2、B3 |
| C2：系统级竞争仍能提供可操作的失败归因 | 整体指标若不能定位 root/child，Manager 无法可靠 retry | 每个被拒候选都有 root-report、Arbiter、corrected/harmed、child diagnostics 和固定 failure type；联合退化能够定位跨 root 交互 | B1、B4 |

**Anti-claim**：收益只是来自换 Prompt、换模型、换数据、降低 Coverage、增加最终评测调用，或在 Dev/heldout/VL-RewardBench 上选择 checkpoint。

本实验不把 node 诊断和系统执行器视为两个竞争系统。Node Worker 只负责发现与解释问题；最终候选接受只由 Unified-Subtree + Global-Arbiter 的全样本 Strict ACC 决定。

## 2. Paper Storyline

- Main paper must prove：相同最终推理协议下，execution-aligned evolution 是否优于 explicit-recursive evolution。
- Main paper supporting evidence：系统级 corrected/harmed、类别结果，以及 accepted/rejected operator 的因果链诊断。
- Appendix can support：逐样本 report transition、joint leave-one-root-out、token/latency、完整失败归因案例。
- Experiments intentionally cut：Root Gate、Child Gate、Create、Merge、Drop、权重搜索、factuality-first Prompt 再消融、跨模型迁移、Dev checkpoint selection、全部候选子集穷举。

## 3. 冻结协议

### 3.1 数据与隔离

| Split | 用途 | Manager 可见 | 选择作用 |
| --- | --- | --- | --- |
| Discovery100 | 触发、ErrorSignature、候选竞争、epoch 提交 | 是 | 唯一演化数据 |
| Dev150 | 每个 epoch 的独立诊断 | 否 | 不早停、不选 checkpoint |
| RLHF-V heldout-500 | 最终 exploratory 验证 | 否 | 不允许反向选择 |
| VL-RewardBench 1,247 | 主要外部评测 | 否 | 不允许反向选择 |

- 使用现有 Discovery-v2 导出，不重新选样，不读取 VL-RewardBench gold 参与演化。
- heldout 和 VL-RewardBench 只能在 discovery 演化与 final report 冻结后访问。
- 即使 Dev150 中间 epoch 更高，也固定运行原定 3–5 epochs，不以 Dev 早停或选 checkpoint。

### 3.2 模型、Prompt 与解码

- Pairwise diagnostic Worker：`Qwen/Qwen3-VL-8B-Instruct`，Prompt v2 cache 版本。
- Unified-Subtree Worker：复用当前正式 Unified-Subtree System/User Prompt 与 parser。
- Global Arbiter：复用 Clean S5-v2 full-report factuality-first Prompt 与 tolerant `A/B/None` parser。
- Manager：沿用现有 `Qwen/Qwen3.5-397B-A17B` Split/Refine profiles。
- Worker endpoint：配置中的 `vllm-8000 + vllm-8001` available-slot pool。
- Worker decoding：`temperature=0.5`、`max_tokens=2048`、不设置 generation seed，与当前正式系统一致。
- Discovery/Dev/heldout 使用 `K=1`；VL-RewardBench 使用冻结的 `K=3` counterbalanced A/B schedule。两者执行图相同，只有重复采样协议不同。

### 3.3 算子与调度

- 初始 Rubric、Split trigger、role-aware child Refine trigger、locked Split retry、Global Memory、Manager schema、3–5 epoch 与 Phase17 保持一致。
- 不启用 Root Boundary Pre-Refine、Create、Merge、Gate 或权重搜索。
- 候选基于同一个 epoch-start Rubric 生成；Split 对同 root 保持优先级。
- node-level 指标只决定候选是否值得生成，不决定候选是否接受。

## 4. 新执行语义

### 4.1 Epoch-start 系统快照

每个 epoch 对 committed Rubric 生成或精确复用：

```text
Node Pairwise diagnostics
        │
        ├─ triggers / node ACC / support / wrong / child diagnostics
        │
        └─ 不产生最终系统判断

5 × Unified-Subtree reports
        │
        ▼
Global Arbiter
        │
        ▼
epoch-start A/B/None + Strict ACC + system feedback
```

固定产物：

```text
epoch_XX/
├── rubric_committed.json
├── diagnostic_pairwise.json
├── unified_subtree_reports.json
├── global_arbiter_predictions.json
├── arbiter_aligned_feedback.json
├── failure_attribution.json
└── summary.json
```

### 4.2 系统错误归因

对每个最终错误样本记录：

1. Global Arbiter 是否输出错误 A/B、`None` 或技术失败；
2. 五棵 root report 的 `answer` 与完整证据；
3. 哪些 root report 错误、缺失或互相冲突；
4. 目标 node 的诊断输出及其适用状态。

Operator evidence 优先使用：

```text
Global Arbiter final wrong
∩ target root report wrong/None
∩ target node diagnostic wrong/None（存在 node 时）
```

若子树报告已提供正确证据而 Arbiter 仍错误，标记为 `arbiter_synthesis_failure`，不把该样本当作 Split/Refine 的主要错误证据。没有足够 attributed errors 的节点可以保留 trigger 诊断，但不强制生成候选。

### 4.3 候选增量评估

候选只修改一个 root 时：

- 复用另外四棵 root 的 epoch-start 报告；
- 只重新生成目标 root 的 Unified-Subtree 报告；
- 用“一份新报告 + 四份冻结报告”重新调用 Global Arbiter；
- before/after 使用同一批样本、顺序、gold、Prompt、parser 和解码协议。

一个 Discovery100 候选的新增 Worker 调用约为：

\[
100\text{ 次目标子树} + 100\text{ 次 Arbiter}=200\text{ 次。}
\]

未修改 root 的报告不得重新生成。缓存 key 至少包含 dataset hash、sample/order、root-subtree hash、Prompt spec、model/checkpoint 和 decoding spec。

## 5. Split / Refine 接受与诊断

### 5.1 主要接受公式

定义 `None` 为错误：

\[
\operatorname{StrictAcc}(R)=\frac{1}{N}\sum_i
\mathbf 1[\operatorname{Arbiter}(U_1(R),\ldots,U_5(R))_i=y_i].
\]

候选接受当且仅当：

1. 所有 required model calls 最终技术有效；
2. `StrictAcc(after) > StrictAcc(before)`，等价于 `corrected > harmed`；
3. candidate identity、Rubric patch 和缓存 provenance 合法。

平局拒绝。Coverage、node ACC、target subtree ACC 和 MacroACC 全部报告，但不覆盖主要 Strict 接受规则。

### 5.2 Refine 诊断

每次 Refine 保存：

- old/new node ACC、support、wrong、coverage；
- old/new target-root report transition；
- old/new Arbiter transition；
- corrected/harmed sample IDs；
- sibling conflict 和 scope expansion；
- failure type 与自然语言归因。

Node ACC 提升但系统不提升时拒绝；node ACC 未提升但系统严格提升时允许接受，并显式记录局部风险。

### 5.3 Split 诊断与 strong child

Split 继续记录 parent、每个 child、cluster、non-target activation、sibling conflict 和 strong-child lock 指标。锁定强 child 仍是 proposal/retry 策略，不是最终接受证据。

Split 失败时，根据 harmed 集合指出：

- 哪些 child 在 harmed 样本上错误或过度激活；
- 哪些 child 保持高 ACC/support，应锁定；
- target-root report 是证据退化、Coverage collapse，还是冲突表达变差；
- Arbiter 是否因新报告覆盖了原有正确结论。

完整 child leave-one-out 不进入 v1 主运行；仅在最终 qualitative diagnosis 中对少量无法解释的 harmed 样本使用。

### 5.4 失败类型

每个 rejection 必须归入：

- `subtree_evidence_regression`
- `coverage_collapse`
- `conflict_amplification`
- `arbiter_synthesis_failure`
- `no_system_effect`
- `joint_interaction_regression`

归因进入下一轮 Manager 的 retry feedback；没有自然语言归因的 rejection 不得进入历史。

## 6. 同步候选与联合提交

1. 所有候选基于 epoch-start Rubric 独立生成和评估。
2. 同一 root 最多保留一个独立 Strict 增益最大的候选；依次以 `system_delta`、`corrected`、`-harmed`、稳定 node ID 打破平局。
3. 将最多五个 root winner 合并，复用各自已生成的新 root reports，重新运行一次 joint Global Arbiter。
4. joint Strict ACC 严格高于 epoch-start 时，整体提交。
5. joint 不提升时，不穷举所有候选子集；只提交独立收益最大的单个候选。
6. joint rejection 额外执行最多五个 leave-one-root-out Arbiter 诊断，用于定位交互，但不据此搜索最佳组合。

这样既保留同步 proposal 的效率，也防止多个单独有效候选组合后共同退化。

## 7. Experiment Blocks

### B0：离线身份审计与旧结果重放

- Claim tested：Anti-claim。
- Dataset：冻结 manifest、现有 Phase17 E4 与 Clean S5-v2 结果。
- Compared systems：现有正式输出 vs 新 evaluator 对同一缓存的重放。
- Metrics：sample/order/hash 完整性，报告数量，parser identity，最终 prediction exact match。
- Success criterion：1,247 样本、`K=3`、18,705 份子树报告与 3,741 Arbiter calls 身份完整；新 evaluator 重放现有 Clean S5-v2 最终结果完全一致。
- Failure interpretation：执行器实现不可信，不允许进入 smoke。
- Priority：MUST-RUN。

### B1：20 条端到端 smoke 与归因验证

- Claim tested：C2。
- Dataset：Discovery100 固定前20条的 smoke subset，不访问 Dev/heldout/VL-RB。
- Compared systems：epoch-start vs 一个 Split candidate 或一个 forced diagnostic candidate。
- Metrics：parse valid、缓存复用、only-one-root regeneration、corrected/harmed、failure-type completeness。
- Success criterion：其他四棵报告逐字节复用；目标 root 和 Arbiter 均生成20条；接受结论可由 stored artifacts 离线重放；所有 rejection 有结构化与自然语言归因。
- Failure interpretation：增量执行或归因链路未打通。
- Priority：MUST-RUN。

### B2：Discovery100 全链路 aligned evolution

- Claim tested：C1、C2。
- Dataset：Discovery100；Dev150 每个 epoch 只诊断。
- Compared systems：Initial Rubric、Phase17 trajectory（历史对照）、aligned-evolution trajectory。
- Metrics：每 epoch Strict ACC/Coverage、operator corrected/harmed、accepted Split/Refine、joint interaction、Dev150 Overall/Macro/领域结果。
- Setup：固定3–5 epochs，不用 Dev 选择 checkpoint。
- Success criterion：流程完成，至少所有候选均按 system-level rule 竞争；若没有候选被接受，也作为有效负结果，不强制放宽阈值。
- Failure interpretation：若 node/local 指标改善但系统拒绝频繁，说明旧演化目标确有错位；若 aligned 候选同样无效，问题更可能在数据、proposal 或 Rubric 表达能力。
- Table / figure target：epoch trajectory + operator transition table。
- Priority：MUST-RUN。

### B3：最终泛化与主对照

- Claim tested：C1。
- Dataset：RLHF-V heldout-500（exploratory）和 VL-RewardBench 1,247（primary）。
- Compared systems：
  1. Initial five-root + 相同 Unified-Subtree/Arbiter；
  2. Phase17 E4 + 相同 Unified-Subtree/Arbiter（复用 Clean S5-v2）；
  3. Aligned-evolution final + 相同 Unified-Subtree/Arbiter。
- Primary metrics：Strict ACC、paired corrected/harmed、paired bootstrap 95% CI、exact McNemar。
- Secondary metrics：OverallAcc、MacroAcc、Coverage、General/Hallucination/Reasoning、source、A/B order disagreement、tokens、latency。
- Success criterion：Treatment 相对 Phase17 E4 的 Strict delta 为正，且 paired 95% CI 下界大于0或 exact McNemar `p<0.05`；Coverage 不单独作为成功标准，因为 `None` 已在 Strict 中计错。
- Failure interpretation：若 Discovery 提升而 VL-RB 不升，说明 aligned objective 仍过拟合 Discovery100；若 heldout 与 VL-RB 方向相反，按 VL-RB 主结论报告分布差异。
- Table / figure target：主结果表与 corrected/harmed 分层图。
- Priority：MUST-RUN。

### B4：失败机制与可解释性

- Claim tested：C2。
- Dataset：B2/B3 的 accepted、rejected、joint-regression artifacts。
- Metrics：六类 failure distribution；root-report/Arbiter transition；child diagnostics；cross-root conflict；leave-one-root-out。
- Success criterion：所有 rejection 可归类，至少展示2–3个完整因果链案例；不要求每个 failure type 都出现。
- Failure interpretation：若大量样本只能归为 unknown，则 system-level feedback 尚不足以支持 Manager retry。
- Table / figure target：`node → subtree report → Arbiter` 因果链案例图。
- Priority：MUST-RUN analysis；child leave-one-out 为 NICE-TO-HAVE。

## 8. Run Order and Milestones

| Milestone | Goal | Runs | Decision Gate | Estimated Cost | Risk |
| --- | --- | --- | --- | --- | --- |
| M0 | 冻结与重放 | freeze、audit、offline replay | Clean S5-v2 exact replay；heldout 未访问 | 纯离线，分钟级 | 历史缓存身份不完整 |
| M1 | 链路 smoke | 20条 baseline/candidate/attribution | 100% 最终可解析；仅目标 root 重算 | 约40次新 Worker calls，加必要 node calls | 缓存 key 或 report schema 漂移 |
| M2 | 完整演化 | Discovery100 3–5 epochs + Dev150 trajectory | 所有 epoch 可恢复；不使用 Dev 选择 | 取决于候选数；每候选约200 calls | 候选数导致成本放大 |
| M3 | 内部最终测试 | heldout-500 | 只报告，不回调 | 从零约3,000 calls；可按 root hash 复用 | 与 VL-RB 分布不一致 |
| M4 | 外部主测试 | VL-RB `K=3` | 完成 paired report 后冻结 | 22,446 logical calls；约2.9小时主 run量级 | 长报告吞吐较低 |
| M5 | 归因分析 | failure/interaction tables | 每个 rejection 有归因 | 大部分离线；joint失败最多500 Arbiter calls/epoch | 归因规则过度解释 |

按既有 S3 + Clean S5-v2 计时，完整 VL-RewardBench 约为136.6分钟子树生成 + 34.8分钟 Arbiter，即约2.9小时主 run，不含技术重试。Evolution 的新增系统调用可按 `200 × candidate_count + joint/diagnostic Arbiter calls` 计算；若全程15个候选，约3,000次候选调用，另加初始/Dev快照和既有 node/Manager 调用。397B Manager 费用沿用原流程，无法从本地 VLLM 计时推导，单独记录 token 与账单。

## 10. Stop / Go Rules

立即停止实现或运行的条件：

- 新 evaluator 不能 exact replay 现有 Clean S5-v2；
- 候选评估重新生成了未修改 root 的报告；
- 技术失败被映射成语义 `None`；
- Dev、heldout 或 VL-RB 进入 Manager context 或 checkpoint selection；
- accepted candidate 的 system delta 无法由保存产物离线重放；
- 同步合并未经过 joint re-evaluation 就直接提交。

继续完整运行的条件：

- smoke 证明增量缓存和 before/after identity 正确；
- rejection attribution 完整；
- Worker 最终 parse valid rate 经同 Prompt retry 达到100%；
- discovery-only 阶段没有访问 heldout/VL-RB。

负结果也必须保留：如果 aligned evolution 没有接受任何操作，或 VL-RB 不提升，不调整阈值后重跑来追求正结果。

## 11. Risks and Mitigations

- **小样本噪声**：Discovery100 上1条即1 pp。保留 paired corrected/harmed，平局拒绝；不通过 Dev 选 checkpoint。
- **test-time compute 混杂**：最终三系统都使用相同 Unified+Arbiter 推理，只有演化过程不同。
- **多候选非可加性**：独立竞争后必须 joint re-evaluation；joint 失败只回退到最佳单候选，不搜索全部子集。
- **Arbiter 错误污染 operator feedback**：将“root 报告正确但 Arbiter 错误”单独归为 synthesis failure，不直接驱动 node 重写。
- **成本膨胀**：只重算修改 root，复用其余四份报告；同 root 每 epoch 最多提交一个候选。
- **strong-child 与新目标错位**：其指标只用于 retry proposal，不作为 system acceptance gate。
- **随机解码残余**：保持正式 decoding 不变并报告 paired CI；不把单个 checkpoint 点估计解释为确定性因果效果。
